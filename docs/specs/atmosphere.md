# Atmospheric scattering spec

상태: 결정됨, 구현 전 (2026-10-11). 구현은 사용자가 시작하라고 할 때 시작한다. 이 스펙의 변경은 먼저 합의한다.

이 스펙은 **공부가 첫 목적**이다. 사용자가 처음 구현해 보는 기술이므로, 기능을 빨리 끝내는 순서가 아니라 **개념을 하나씩 이해하며
쌓는 순서**로 짠다. 결과물(샌드박스의 하늘과 대기 원근)은 그 과정의 산물이다.

## 1. 목표

### 만드는 것

샌드박스의 씬에 물리 기반 대기를 더한다.

- **하늘**: 지금의 단색 배경(`NvRenderer.clear_color`) 대신 해의 방향에 따라 바뀌는 하늘. 낮에는 파랗고, 해가 낮으면 지평선이
  붉어지고, 해 주변에 후광이 있고, 해 원반이 보인다. 지평선 아래는 행성의 지면이다.
- **햇빛의 색**: 해가 낮을수록 지면에 닿는 햇빛이 붉고 어두워진다.
- **대기 원근(aerial perspective)**: 먼 물체가 하늘 색으로 흐려진다.
- **하늘의 주변광**: 씬의 고정된 주변광(`lighting`의 `ambient`, chess_scene.md) 대신 하늘에서 오는 빛.

해는 씬의 첫 directional light다(`shadows.md`와 같다). 그 노드를 기즈모로 돌리면 시각이 바뀌고, 그 노드에 `spin`을 달면 Play에서
하루가 흐른다.

### 배우는 것

다 끝났을 때 사용자가 설명할 수 있어야 하는 것:

- 빛의 단위(radiance, irradiance)와 이 엔진의 단위가 그와 어떻게 다른가.
- 참여 매질(participating media)의 세 계수(산란, 흡수, 소멸)와 위상 함수, Beer-Lambert 법칙.
- 하늘이 왜 파랗고, 해질녘이 왜 붉고, 연무가 왜 희고, 해 주변이 왜 밝은가: 식으로.
- 산란 적분을 수치로 푸는 방법(레이 마칭)과 걸음 수가 정확도와 비용에 주는 영향.
- 다중 산란과 Hillaire의 근사가 무엇을 버리고 무엇을 얻는가.
- LUT(look-up table)로 적분을 미리 계산하는 방법: 대칭성으로 차원 줄이기, 매개화(parametrization), 해상도와 오차.
- 같은 적분이 하늘, 대기 원근, 주변광에 어떻게 다시 쓰이는가.
- GPU에서: compute 패스로 텍스처 만들기, 3D 텍스처, 프레임마다/값이 바뀔 때만 다시 계산하는 판단.
- 비용: 이 기법의 비용 모델(어디에 몇 번의 계산과 몇 번의 메모리 읽기가 드나), GPU 시간을 믿을 만하게 재는 법, 최적화마다 무엇을 내주고
  무엇을 얻나.

## 2. 공부의 원칙

1. **느린 정답부터, 최적화는 나중에.** 각 개념은 먼저 가장 곧은 형태(픽셀마다 적분)로 만든다. 식이 코드에 한 줄씩 그대로 보인다.
   LUT는 그 뒤에 하나씩, **같은 답을 빠르게 내는 최적화**로 넣는다.
2. **최적화는 끄고 켤 수 있다.** LUT마다 끄는 토글이 있어, 끄면 곧은 적분으로 돌아간다. 다 만든 뒤에도 남긴다. 토글과 차이
   보기로 그 LUT가 무엇을 바꿨는지(오차가 어디에 몰리는지)와 얼마를 아꼈는지(GPU 시간)를 직접 본다.
3. **정답의 사슬.** C 코드(CPU)가 첫 정답이다: 디버거로 따라가고, 값을 찍고, ctest로 손 계산과 맞출 수 있다. GPU의 곧은 적분은
   C와 맞추고(프로브), GPU의 LUT 경로는 GPU의 곧은 적분과 맞춘다(차이 보기). 어느 고리가 틀렸는지 늘 좁힐 수 있다.
4. **한 단계에 새 개념 하나.** 단계는 작게 나누고, 단계마다 화면에 새로 보이는 것이 있다.
5. **예측하고 확인한다.** 실험은 "이렇게 바꾸면 어떻게 될까?"를 먼저 적고 확인하는 형태다. 예측이 틀린 곳이 공부할 곳이다.
6. **식과 코드를 잇는다.** 함수마다 주석에 구현하는 식과 이 스펙 "이론"의 번호를 적는다. 이 모듈은 공부를 위해 코딩 표준보다
   주석이 많다: 식 자체를 주석으로 쓴다.
7. **개념의 핵심은 직접 쓴다.** 읽기만 한 코드보다 직접 쓴 코드가 오래 남는다. 단계마다 그 단계의 개념이 담긴 함수 한두 개(각 5~20줄)를
   사용자가 C로 직접 쓴다(아래 "직접 쓰기"). 개념이 없는 코드(WGSL 이식, 패스, 파이프라인, 바인딩, 샌드박스, UI, 저장, 시험의 틀)는
   Claude가 쓴다.
8. **이해를 검증받는다.** 코드가 돌아가는 것과 이론을 이해한 것은 다르다. 단계마다 사용자가 이론 문제(설명, 손 계산, 유도, 참/거짓)에
   자기 말로 답하고 Claude가 채점한다. 사후 검증을 통과해야 다음 단계로 간다(3절 "이해 검증"). 문제와 실험에는 답을 적지 않는다.

대가: 곧은 적분과 LUT 경로가 함께 있어 코드가 늘고(약 30%), 적분이 C와 WGSL 두 벌이다. 두 벌은 같은 구조와 이름으로 써서 나란히
읽을 수 있게 한다. 이 대가는 공부와 시험(정답의 사슬) 둘 다에 쓰이므로 받아들인다.

## 3. 단계를 진행하는 방법

정함(2026-10-11): **Claude가 단계마다 코드를 쓰고, 사용자가 읽고 질문한 뒤 다음 단계로 간다. 다만 개념의 핵심 함수는 사용자가 연습으로
직접 쓴다.** 무엇이 연습이고 무엇이 Claude의 몫인지는 단계마다 "직접 쓰기"에 적는다.

| 누가 | 무엇을 |
|---|---|
| 사용자 | 단계의 "직접 쓰기" 함수의 본문(C). 식을 코드로 옮기는 부분만: 광선-구 교차, 광학 깊이, 산란 적분의 루프, 위상 함수, LUT의 매개화, 다중 산란의 적분, 반구 적분, 샘플 분포 |
| Claude | 그 밖의 모든 것: 함수의 선언과 식을 적은 주석, 연습 시험, 사용자 함수의 WGSL 이식, compute와 렌더 패스, 파이프라인, 바인딩, 샌드박스(씬 파일, View 탭, 저장, undo), 공부 도구, Playwright 시험, 문서 |

한 단계는 이렇게 흐른다.

1. **미리 읽기와 연습 준비.** Claude가 그 단계의 "배울 것", 이론 번호, 읽을거리의 해당 부분, 실험에서 예측해 볼 질문을 보낸다. 같은 커밋에
   연습을 올린다:
   - `engine/atmosphere.c`에 연습 함수의 선언, 식과 단위를 적은 주석, 비어 있는 본문(`// EXERCISE:` 표시, 0을 돌려준다). 아직 아무도 부르지
     않으므로 CI는 초록이다.
   - `tests/atmosphere_exercise.c`: 그 단계의 연습 시험(정답을 알려 주지 않고 성질을 검사한다: 손 계산 값, 극한, 대칭, 수렴, 왕복).
     ctest에 등록하지 않는다. `engine/atmosphere.c`를 직접 `#include`해 내부 함수도 부른다. Emscripten 없이 바로 돈다(Linux 가정):

     ```sh
     cc -std=c17 -Wall -Wextra -I. tests/atmosphere_exercise.c -lm -o /tmp/exercise && /tmp/exercise
     ```
2. **사전 점검.** 코드를 쓰기 전에, Claude가 그 단계의 이론으로 짧은 문제 2~3개를 낸다(코드로 옮길 식을 이해했는지). 답은 채팅에 쓴다.
   보완이 필요하면 직접 쓰기 전에 그 부분을 다시 본다.
3. **직접 쓰기.** 사용자가 본문을 쓰고 연습 시험이 통과할 때까지 고친다. 브랜치에 커밋하거나 채팅에 붙인다. 막히면 힌트를 세 단계로
   청한다(Claude는 정답을 바로 주지 않는다):
   - 힌트 1: 무엇을 계산해야 하나(입력, 출력, 단위).
   - 힌트 2: 이론의 어느 식이 코드의 어느 줄이 되나.
   - 힌트 3: 의사 코드.

   원하면 "건너뛰기"로 Claude가 쓴다(그 단계의 "구현 결과"에 적는다).
4. **리뷰.** Claude가 사용자의 함수를 리뷰한다: 식과 맞나, 수치 문제(경계, 0으로 나누기, 걸음의 중점), 코딩 표준. 참조 구현(Hillaire,
   Bruneton)과 다른 곳이 있으면 어느 쪽이 왜 나은지 설명한다. 고칠 것은 사용자가 고친다. 리뷰가 끝난 사용자의 함수가 엔진의 코드가 된다.
5. **구현.** Claude가 나머지를 쓴다. 커밋은 읽는 순서대로 나눈다: 사용자 함수의 WGSL 이식(같은 이름, 같은 구조로 나란히 읽히게) → 렌더러
   연결 → 샌드박스와 공부 도구. 연습 시험의 검사는 `tests/atmosphere_test.c`(ctest)로 옮긴다.
6. **해설.** Claude가 이론과 코드의 대응(식 → 함수, 파일과 줄), 읽기 순서, 실행 방법을 보낸다. 배포된 Debug 빌드의 주소도 보낸다
   (CI가 브랜치마다 Pages에 올린다). 해설은 Claude가 쓴 코드 가운데 개념이 있는 곳(WGSL 이식과 셰이더의 흐름)에 집중하고, 배관은 짧게 넘긴다.
7. **실험.** 사용자가 실험마다 예측을 먼저 적어 보내고 실험한다. 예측과 다른 결과는 왜 다른지 사용자가 먼저 설명해 보고, Claude가 그 설명을
   채점한다. 궁금한 것은 언제든 묻는다. 필요하면 Claude가 실험 도구를 고친다.
8. **사후 검증.** 사용자가 그 단계의 "검증 문제"에 답한다. Claude가 채점한다(아래 "이해 검증"). 통과하면 다음으로 간다.
9. **기록.** 그 단계에서 배운 것, 틀렸던 곳(연습과 검증에서 틀린 곳 포함), 예측과 달랐던 실험, 검증 결과, GPU 시간을 이 스펙의
   "구현 결과"에 짧게 적는다. GPU 시간은 잰 환경(백엔드, 기기, 해상도)과 함께 적고, D3D12 빌드가 준비되기 전의 숫자는 참고로만 적는다.
10. **다음 단계.** 사후 검증을 통과하고 사용자가 넘어가자고 할 때 넘어간다. 다음 단계의 미리 읽기는 앞 단계들의 문제 1~2개로 시작한다
    (기억에서 꺼내 보기: 특히 전에 틀렸던 것).

### 이해 검증

**문제의 종류**

| 종류 | 무엇을 보나 | 예 |
|---|---|---|
| 설명 | 현상을 이론의 말로 설명하나 | "지평선이 천정보다 밝고 흰 이유는?" |
| 손 계산 | 식을 숫자로 쓸 수 있나(과정을 보인다, 허용 오차는 문제에 적는다) | "천정 투과율을 계수와 스케일 높이로" |
| 유도 | 식이 어디서 오는지 아나 | "등비급수에서 1 / (1 − f_ms)를" |
| 참/거짓 | 흔한 오개념을 피하나(이유와 함께 답한다) | "해질녘이 붉은 것은 Mie 산란 때문이다" |
| 예측 | 실험 전에 결과를 맞히나, 틀리면 왜 틀렸는지 설명하나 | 각 단계의 실험 |
| 전이 | 배운 것을 새 상황에 쓰나 | 종합 검증의 화성 |

**채점**

- 채점 기준(답에 꼭 있어야 할 요소와 흔한 오개념)은 스펙에 쓰지 않는다: 미리 보면 검증이 되지 않는다. Claude가 이론 절과 읽을거리로 기준을
  세워 채점하고, 채점한 뒤 기준을 보여 준다.
- 판정은 셋이다.
  - **통과**: 핵심 요소가 모두 있고 오개념이 없다. 손 계산은 방법이 맞고 값이 허용 오차 안이다.
  - **보완**: 대체로 맞지만 빠진 요소나 작은 오개념이 있다. Claude가 그 부분만 겨누는 꼬리 질문을 한다(답을 주지 않는다). 두 번까지.
  - **다시**: 핵심이 틀렸다. Claude가 다시 볼 곳(이론 번호, 읽을거리, 실험)을 가리키고, 나중에 같은 개념을 다른 문제로 다시 낸다.
- 답은 사용자의 말로 쓴다. 스펙이나 자료를 보지 않고 답하기를 권한다(기억에서 꺼내야 남는다). 본 경우는 그렇다고 적는다.
- 사후 검증은 그 단계의 검증 문제를 모두 통과(보완 뒤 통과 포함)하면 통과다. 사용자가 원하면 통과 전에 넘어갈 수 있고, 남은 문제는
  "구현 결과"에 적어 다음 단계의 미리 읽기에서 다시 낸다.
- 기록: 단계마다 "검증: 문제 n개, 바로 통과 a, 보완 뒤 통과 b, 다시 c. 고친 오개념: …".

## 4. 이론

단계들이 번호로 가리킨다. 단위는 길이 km, 계수 1/km.

**0. 빛의 단위.** radiance L은 한 방향에서 오는 빛의 세기(W/(m²·sr)), irradiance E는 면에 떨어지는 빛의 총량(W/m²). 해는 아주
작아서 E_sun 하나로 쓴다. 흰 Lambert 면이 E를 정면으로 받으면 L = E / π로 빛난다. 이 엔진의 메시 셰이더에는 1/π가 없다
(`light_color * diffuse`): 엔진의 값은 "π × radiance"다. 그래서 하늘의 radiance에도 π를 곱해야 메시와 같은 단위가 된다.

**1. 기하.** 행성은 중심이 (0, −R_g, 0)인 공(R_g = 6360 km), 대기는 반지름 R_t = 6460 km까지. 점 p에서 방향 v로 가는 광선과
반지름 r인 구의 교차는 t² + 2(p·v)t + (|p|² − r²) = 0의 근이다. 시선은 대기 안에 있는 구간만 적분하고, 행성에 닿으면 거기서 끝난다.
높이 h = |p| − R_g, 천정각의 코사인 μ = (p·v) / |p|.

**2. 매질.** 세 성분이 섞여 있다. 계수 = 지면의 값 × 밀도 d(h).
- Rayleigh(공기 분자): 산란만, d = exp(−h / 8). 파장에 크게 의존한다(λ⁻⁴ 근사: 파랑이 빨강의 약 6배).
- Mie(에어로졸, 연무): 산란과 약간의 흡수, d = exp(−h / 1.2). 파장에 거의 무관하다(회색).
- 오존: 흡수만, d = max(0, 1 − |h − 25| / 15). 초록에서 주황까지를 흡수하고 파랑은 거의 흡수하지 않는다.
H(8 km, 1.2 km)는 스케일 높이: H만큼 오를 때마다 밀도가 1/e가 된다.

**3. 투과율 (Beer-Lambert).** 두 점 사이를 지나며 남는 빛의 비율. σ_t = σ_s + σ_a(소멸 = 산란 + 흡수).
T(a, b) = exp(−τ), τ = ∫ₐᵇ σ_t(x) dx(광학 깊이). 천정 방향은 τ가 작고 지평선 방향은 Rayleigh 공기를 약 35배(√(πR_g / 2H)) 지나 τ가 크다: 파랑이 먼저
빠져 해질녘의 햇빛이 붉다.

**4. 위상 함수.** 산란된 빛이 각 θ만큼 꺾일 확률 밀도(모든 방향으로 적분하면 1).
- Rayleigh: p_R(θ) = 3 / (16π) · (1 + cos²θ). 앞뒤가 대칭이다.
- Mie(Cornette-Shanks): p_M(θ) = 3 / (8π) · (1 − g²)(1 + cos²θ) / ((2 + g²)(1 + g² − 2g·cosθ)^{3/2}). g가 클수록 앞쪽(해 주변)에 몰린다.

**5. 단일 산란.** 시선 위의 각 점 x에서 햇빛이 한 번 꺾여 눈으로 오는 빛을 더한다.
L₁ = ∫₀^{t_max} T(c, x) · Σ_i σ_s,i(x) p_i(θ) · T(x, 해) · V(x) · E_sun dt.
V(x)는 x에서 해가 행성에 가려지면 0. 수치 적분은 구간을 N걸음으로 나눠 각 걸음 가운데에서 값을 구한다(중점 규칙). 걸음마다
T(x, 해)도 적분이므로 곧은 구현의 비용은 픽셀 × N × M이다.

**6. 지면과 해 원반.**
- 지면(지평선 아래 시선): 행성의 표면이 반사율 a로 빛난다. L_ground = a / π · E_sun · T(지면, 해) · max(μ_sun, 0) (뒤에 하늘의 빛이 더해진다: 10번).
  그 빛이 눈까지 오며 T(c, 지면)만큼 줄고, 그 사이의 공기가 5번의 산란을 더한다.
- 해 원반: 시직경 α 안의 방향은 L_sun = E_sun · T(c, 해) / Ω, Ω = 2π(1 − cos(α / 2)). 가장자리로 갈수록 어둡게(limb darkening) 한다.
  Ω가 아주 작아 L_sun은 하늘보다 수만 배 밝다.

**7. 다중 산란 (Hillaire 2020).** 두 번 이상 꺾인 빛. 정확히 하려면 모든 방향의 적분이 겹겹이 필요하다. Hillaire의 근사:
- 2차 이상의 산란은 방향에 거의 무관하다(등방)고 본다.
- 한 점 주변이 다 같은 높이의 공기라고 보면, 빛이 한 번 더 산란될 때마다 같은 비율 f_ms가 돌아온다.
- 그러면 모든 차수의 합은 등비급수다: L₂ + L₂·f_ms + L₂·f_ms² + … = L₂ / (1 − f_ms).
다중 산란 LUT가 높이와 해의 천정각마다 Ψ_ms = L₂ / (1 − f_ms)를 담고, 5번의 적분 안에 σ_s(x) · Ψ_ms 항이 더해진다.
버리는 것: 다중 산란의 방향성. 그래서 연무가 아주 짙으면 틀린다(실험 4-d: 경로 추적과 비교).

**8. 대기 원근.** 물체까지의 시선에 5번(과 7번)을 t_max = 물체까지의 거리로 적분한 산란 S와 투과율 T. 화면 색 = 물체의 색 · T + S.
하늘은 "물체가 없는 시선"의 대기 원근이다: 같은 적분이다.

**9. LUT와 매개화.** 적분의 결과가 소수의 변수에만 달려 있으면 미리 계산해 텍스처에 담는다.
- 대칭성: 행성이 공이므로 투과율은 위치와 방향 전체가 아니라 (h, μ) 두 값에만 달려 있다. 다중 산란은 (h, μ_sun).
- 매개화: 텍스처의 uv를 그 값으로 어떻게 펼치나. 값이 빨리 변하는 곳(지평선 근처)에 텍셀을 많이 둔다. 균일하게 펼치면 지평선
  근처의 오차가 커진다(실험 3-c).
- 언제 다시 계산하나: 변수에 들어가지 않는 것이 바뀌면 다시 만든다. 투과율 LUT는 대기 값이 바뀔 때만, 하늘 뷰 LUT는 카메라 높이와
  해 방향이 들어가므로 매 프레임.

**10. 하늘의 조도(주변광).** 법선 n인 면이 하늘에서 받는 빛: E_sky(n) = ∫ L(ω) max(0, n·ω) dω(반구에서 코사인 가중 적분).
위를 보는 면은 하늘 전체를, 아래를 보는 면은 지면에서 튄 빛을 받는다. 그늘 속이 파랗게 보이는 이유다.

**11. 비용 모델과 측정.**
- 일의 양: 곧은 하늘은 픽셀 수 × N × M번 매질을 계산한다. 투과율 LUT가 있으면 픽셀 수 × N(안쪽 적분이 텍스처 읽기 한 번), 하늘 뷰 LUT가
  있으면 텍셀 수(192 × 108) × N에 픽셀마다 읽기 한 번이다. LUT는 일을 "화면의 크기"에서 "LUT의 크기"로 옮긴다. 그래서 LUT가 화면보다 작을
  때, 그리고 LUT를 다시 만드는 횟수가 적을 때만 이득이다.
- 계산과 대역폭: 셰이더의 시간은 계산(지수 함수, 곱셈)과 메모리(텍스처와 버퍼를 읽고 쓰기) 가운데 더 막힌 쪽이 정한다. 걸음을 줄이면
  계산이, 텍스처를 작게 하거나 형식을 줄이면(16비트 대 32비트) 대역폭이 준다. 어느 쪽이 막혔는지 모르고 고치면 효과가 없다.
- 같은 정확도를 더 적은 걸음으로: 걸음의 수를 시선의 길이에 맞추고(짧은 시선은 적게), 걸음을 밀도가 빨리 변하는 곳(카메라 가까이, 지면
  가까이)에 촘촘히 둔다. 오차는 걸음의 수뿐 아니라 걸음을 어디에 두느냐에 달려 있다.
- 다시 하지 않기: 입력이 바뀌지 않은 LUT는 다시 만들 필요가 없다. 무엇이 입력인지(이론 9) 정확히 알아야 틀리지 않는다.
- 보이지 않는 픽셀은 계산하지 않기: 하늘을 불투명 메시 뒤에 그리고 깊이로 걸러, 메시에 가린 픽셀의 하늘을 계산하지 않는다.
- 측정: GPU 타임스탬프는 패스의 시작과 끝 사이를 잰다. 값은 클럭 변화, 발열, 다른 일 때문에 흔들리므로 데우고(warm-up) 여러 프레임을
  평균하고, 한 번에 하나만 바꾸고, 같은 기기와 같은 해상도에서 비교한다. 패스 안의 일부(씬 패스 안의 하늘)는 따로 잴 수 없으므로 그것을
  끄고 켠 차이로 잰다.

## 5. 단계

단계마다: **배울 것**, **이론**(4절의 번호), **직접 쓰기**(사용자의 연습, 3절), **만드는 것**(Claude), **볼 것**, **실험**(예측 → 확인), **검증 문제**(사후 검증, 3절), **읽기 순서**, **다음 단계의 동기**. 실험의 값은 View 탭의 Atmosphere 섹션(대기 값)과 Atmosphere study 섹션(6절)에서 바꾼다.

### 0단계: 단위, 기하, 투과율 (CPU만)

- **배울 것**: 엔진의 빛 단위, 광선-구 교차, 밀도와 스케일 높이, 광학 깊이와 투과율, 해질녘이 붉은 이유.
- **이론**: 0, 1, 2, 3.
- **직접 쓰기**:
  - `ray_sphere(origin, direction, radius)`: 광선과 구의 두 교차 거리(이차 방정식, 이론 1). 결과 구조체(`ok`, 가까운 t, 먼 t). 약 10줄.
    검사: 맞히기, 빗나가기, 구 안에서 출발, 스치기.
  - `medium_at(atmosphere, height)`와 `optical_depth(atmosphere, origin, direction, length, steps)`: 높이에서 세 성분의 밀도와 계수(이론 2),
    그리고 중점 규칙으로 소멸 계수를 적분(이론 3). 합쳐 약 20줄. 검사: 천정 투과율이 손 계산과 1% 안, 걸음을 늘리면 수렴, 길이 0이면 0.
- **만드는 것**:
  - `engine/atmosphere.h`, `engine/atmosphere.c`: `NvAtmosphere`, 지구 기본값, 연습 함수의 선언과 연습 시험, 사용자의 함수로 만드는
    `nv_atmosphere_transmittance`.
  - `tests/atmosphere_test.c`(ctest).
  - 렌더러: `frame.light_color`에 해 방향의 투과율을 곱한다(햇빛의 색).
  - 샌드박스: 씬 파일 `lighting` 블록 안의 `atmosphere` 블록(읽기, View 탭, 저장 `ATMO`, undo), 쇼케이스 파일에 블록. Study 섹션의
    그래프 둘: 높이별 밀도, 해의 고도별 투과율.
  - 하늘은 아직 `clear_color`다.
- **볼 것**: 기즈모로 해를 낮추면 바닥과 캐릭터가 주황으로, 지평선 아래로 가면 검게 바뀐다. 그래프에서 파랑이 먼저 떨어진다.
- **실험**:
  - a. 해의 고도 90° → 10° → 2°. 예측: 어느 고도에서 바닥이 눈에 띄게 주황이 될까? 투과율 그래프에서 그 고도의 R, G, B를 읽는다.
  - b. `rayleigh` 3배. 예측: 같은 고도에서 더 붉어질까, 더 어두워질까?
  - c. `mie` 10배. 예측: 색이 바뀔까, 밝기만 바뀔까?
  - d. `ozone` 0. 예측: 바닥의 색에 차이가 클까?
- **검증 문제**:
  1. [손 계산] 천정 방향 투과율이 (0.94, 0.87, 0.76)인 이유를 계수와 스케일 높이로 손 계산할 수 있나?
  2. [손 계산] 공기의 절반이 몇 km 아래에 있나?
  3. [설명] 해가 지평선에 닿기 전부터 바닥이 어두워지는 이유는?
  4. [설명] 엔진의 `light_color`가 radiance가 아니라 "π × radiance"의 단위라는 것은 무슨 뜻인가?
  5. [유도] 광선 p + t·v와 구 |x|² = r²에서 t의 이차식을 유도하라. 근이 없으면, 근이 둘 다 음수면 무슨 뜻인가?
  6. [참/거짓] "빛은 지나온 거리에 비례해 줄어든다." 이유와 함께.
- **읽기 순서**: `NvAtmosphere`(필드의 단위) → 밀도 함수 → 광선-구 교차 → 광학 깊이 → `nv_atmosphere_transmittance` → ctest → 렌더러에서 쓰는 곳.
- **다음의 동기**: 해에서 지면까지 오는 빛은 알았다. 그 빛의 일부가 시선 쪽으로 꺾이는 것이 하늘이다.

### 1단계: 곧은 하늘, Rayleigh 단일 산란

- **배울 것**: 산란 적분, Rayleigh 위상 함수, 중점 규칙과 걸음 수, 곧은 구현의 비용(픽셀 × N × M).
- **이론**: 4(Rayleigh), 5.
- **직접 쓰기**:
  - `rayleigh_phase(cos_theta)`: 1줄(이론 4).
  - `nv_atmosphere_sky`의 산란 루프: 걸음마다 위치, 매질, 카메라까지의 투과율, 해까지의 투과율(`optical_depth`), 위상 함수를 곱해 더한다
    (이론 5). 약 20줄. 시선의 구간과 결과 구조체는 Claude가 준비한다. 검사: 얇은 대기의 극한(L ≈ σ_s · p · E · 길이), 천정이 파랗고
    지평선이 밝다, 걸음을 늘리면 수렴.
- **만드는 것**:
  - C: `nv_atmosphere_sky`의 틀(시선이 대기를 지나는 구간, 결과 구조체). 산란 루프는 직접 쓰기.
  - 사용자의 루프를 WGSL로 옮긴다(같은 이름, 같은 구조).
  - 하늘 패스: 화면 삼각형, 픽셀마다 시선을 N걸음, 걸음마다 해 방향을 M걸음 적분한다(LUT 없음). 행성에 닿는 시선은 거기서 멈춘다(지면은 아직 검다).
  - Study 섹션: 걸음 수 슬라이더, 성분 보기(`FINAL`, `TRANSMITTANCE`, `SINGLE`), 프로브, 높이 오프셋, GPU 시간.
- **볼 것**: 파란 하늘, 천정보다 밝고 흰 지평선. 해를 낮추면 해 쪽 지평선이 붉어진다. 해 주변은 아직 특별히 밝지 않다.
- **실험**:
  - a. 걸음 수 64 → 4. 예측: 어디부터 틀어질까?
  - b. 프로브를 천정과 지평선에 두고 GPU 값과 C 값을 비교한다. 차이가 1% 안이어야 한다(정답의 사슬 첫 고리).
  - c. 높이 오프셋 0 → 10 → 40 km. 예측: 하늘의 밝기와 색은?
  - d. 해상도 Scale 1과 4에서 GPU 시간. 예측: 비용이 픽셀 수에 비례할까?
- **검증 문제**:
  1. [설명] 같은 Rayleigh 산란으로 하늘은 파랗고 해질녘의 지평선은 붉다. 둘을 한 식으로 설명할 수 있나?
  2. [설명] 지평선이 천정보다 밝고 흰 이유는?
  3. [설명] 왜 `T(x, 해)`가 적분 안에 있나? 빼면 무엇이 틀리나?
  4. [손 계산] 1080p에서 N = 32, M = 16이면 프레임당 지수 함수를 몇 번 계산하나?
  5. [손 계산] 대기가 아주 얇다고 보고(투과율 ≈ 1), 해가 천정에 있을 때 천정 방향 Rayleigh 단일 산란의 파랑 채널을 E_sun = 1로 어림하라(10% 안).
  6. [참/거짓] "하늘이 파란 것은 공기가 빨간빛을 흡수하기 때문이다." 이유와 함께.
- **읽기 순서**: C의 `nv_atmosphere_sky` → WGSL의 같은 이름의 함수(나란히) → 하늘 패스의 정점/프래그먼트 → 렌더러 연결.
- **다음의 동기**: 해 주변의 후광, 연무, 지평선 아래가 없다. 그리고 비싸다(실험 d).

### 2단계: Mie, 오존, 해 원반, 지면

- **배울 것**: Mie 위상 함수와 비등방성 g, 산란과 흡수의 차이, 오존 층, 해 원반의 radiance, 지면의 반사.
- **이론**: 2, 4(Mie), 6.
- **직접 쓰기**:
  - `cornette_shanks_phase(cos_theta, g)`: 약 5줄(이론 4). 검사: 구 위에서 적분하면 1, g = 0이면 Rayleigh 위상 함수와 같다, g가 크면 앞쪽이 크다.
  - 산란 루프에 Mie 항을 더한다(몇 줄). 오존은 `medium_at`에 이미 있다(0단계). 해 원반과 지면은 Claude가 쓴다(새 개념이 적은 기하).
- **만드는 것**: 적분에 Mie와 오존, 해 원반, 지면. C와 WGSL 둘 다. 성분 보기 `RAYLEIGH`, `MIE`. 그래프: 위상 함수(각도별, 로그 축).
- **볼 것**: 해 주변의 흰 후광, 해 원반(bloom으로 빛난다), 지평선 아래의 지면.
- **실험**:
  - a. `mie_anisotropy` 0 → 0.95. 예측: 후광의 크기와 밝기는? 위상 함수 그래프와 비교한다.
  - b. `mie` 10배. 예측: 하늘이 더 파래질까, 희어질까?
  - c. 해 고도 2°에서 `ozone` 1과 0의 천정 색. 예측: 오존이 없으면 해질녘 천정은 무슨 색일까?
  - d. `sun_disk` 0.545° → 5°. 예측: 원반이 커지면 원반의 밝기는?
- **검증 문제**:
  1. [설명] 연무가 하늘을 희게 만드는 이유를 계수의 파장 의존으로 설명할 수 있나?
  2. [설명] 오존은 흡수만 하는데 왜 해질녘에만 눈에 띄나?
  3. [설명] 해 원반의 radiance가 하늘보다 수만 배 큰 이유는?
  4. [설명] 지면의 식에 왜 1/π가 있고, 엔진 단위에서는 어떻게 되나?
  5. [유도] Rayleigh 위상 함수를 구 위에서 적분하면 1임을 보여라.
  6. [손 계산] g = 0.8에서 p_M(0°) / p_M(180°)를 구하라(5% 안).
  7. [참/거짓] "해질녘이 붉은 것은 Mie 산란 때문이다." 이유와 함께.
- **다음의 동기**: 정답이 생겼다. 이제 같은 답을 빠르게: 가장 안쪽의 적분(해 방향 투과율)부터.

### 3단계: 투과율 LUT

- **배울 것**: 미리 계산, 대칭성으로 차원 줄이기, (h, μ)의 매개화, 선형 필터의 오차, LUT를 다시 만드는 조건.
- **이론**: 3, 9.
- **직접 쓰기**: `transmittance_uv_from(height, mu)`와 그 역 `transmittance_height_mu_from(uv)`: 지평선 근처를 촘촘히 하는 매핑(이론 9,
  Bruneton 2017의 매개화). 합쳐 약 15줄. 검사: 왕복이 맞다, 지평선 방향이 기대한 v에 온다, 균일 매핑보다 지평선 근처에 텍셀이 많다.
- **만드는 것**: 투과율 LUT compute 패스, 토글 "Transmittance LUT", 차이 보기, Textures 탭 항목, 대기 compute의 타임스탬프. 공부용
  분기 "균일 매핑"(지평선을 촘촘히 하지 않는 매핑).
- **볼 것**: 그림은 거의 같고 GPU 시간이 준다. 차이 보기에서 오차가 지평선 근처에 모인다. Textures 탭에서 LUT의 모양.
- **실험**:
  - a. 토글을 끄고 켜며 GPU 시간. 예측: 얼마나 줄까?
  - b. 차이 보기의 배율을 키워 오차가 어디 있는지 본다.
  - c. "균일 매핑"을 켠다. 예측: 오차가 어디서 커질까?
  - d. 해를 돌린다 / `rayleigh`를 바꾼다. Study 섹션의 "LUT를 만든 횟수"가 언제 오르나?
- **검증 문제**:
  1. [설명] 투과율이 위치 3개와 방향 2개가 아니라 (h, μ) 두 값에만 달린 이유는?
  2. [설명] 해를 돌려도 LUT를 다시 만들지 않아도 되는 이유는?
  3. [설명] LUT의 v축(μ)을 지평선 근처에서 촘촘히 하는 이유는?
  4. [손 계산] 높이 1 km에서 지평선 방향의 μ를 구하라(R_g = 6360 km, 1% 안). 그 값이 0이 아닌 이유는?
- **다음의 동기**: 하늘이 실제보다 어둡다(특히 해에서 먼 쪽, 해가 진 뒤). 한 번만 꺾인 빛만 셌기 때문이다.

### 4단계: 다중 산란 LUT

- **배울 것**: 산란의 차수, 등방 근사, 등비급수, 근사의 한계.
- **이론**: 7.
- **직접 쓰기**: `multiple_scattering_psi(atmosphere, height, mu_sun)`: 방향 64개에 대해 L₂와 f_ms를 적분하고 L₂ / (1 − f_ms)를
  돌려준다(이론 7). 약 20줄. 검사: 0 < f_ms < 1, `mie`를 키우면 Ψ가 커진다, 해가 지평선 아래 깊으면 작다. 경로 추적기는 Claude가 쓴다
  (원하면 자유 비행 거리 샘플링 `−ln(1 − u) / σ_t` 몇 줄을 추가 연습으로).
- **만드는 것**: 다중 산란 LUT compute 패스(텍셀마다 방향 64개를 workgroup이 나눠 적분), 적분에 Ψ_ms 항, 토글 "Multiple scattering",
  성분 보기 `MULTIPLE`. C 판에도 같은 항. C의 몬테카를로 경로 추적(`nv_atmosphere_path_trace`, Debug 빌드의 Study 섹션).
- **볼 것**: 하늘이 밝아진다. 해가 진 직후에도 하늘이 완전히 검지 않다. 짙은 연무에서 차이가 크다.
- **실험**:
  - a. 토글을 끄고 켠다. 예측: 어느 쪽 하늘이 가장 많이 바뀔까?
  - b. `mie` 20배에서 토글. 예측: 단일 산란만으로는 짙은 안개가 어떻게 보일까?
  - c. 해 고도 −3°에서 `SINGLE`과 `MULTIPLE` 보기.
  - d. **경로 추적과 비교**(Debug 빌드): 프로브 방향에서 C의 몬테카를로 경로 추적(모든 차수의 산란, 근사 없음)을 돌려 근사와 비교한다.
    값이 프레임마다 쌓이며 수렴하는 것을 본다(잡음은 경로 수의 제곱근에 반비례한다). 예측: `mie` 1과 20에서 근사의 오차는?
- **검증 문제**:
  1. [설명] 2차 이상의 산란을 등방이라 봐도 되는 이유는? 언제 안 되나?
  2. [설명] f_ms는 무엇의 비율이고, 1 / (1 − f_ms)는 왜 나오나?
  3. [설명] 이 LUT가 해의 천정각과 높이 두 값에만 달린 이유는?
  4. [유도] "매번 같은 비율 f_ms가 돌아온다"에서 1 / (1 − f_ms)를 유도하라. f_ms가 1에 가까워지면 무슨 일이 생기나?
  5. [참/거짓] "다중 산란을 더하면 하늘의 색은 그대로이고 밝기만 는다." 이유와 함께.
- **다음의 동기**: 하늘은 맞지만 여전히 픽셀마다 N걸음을 적분한다.

### 5단계: 하늘 뷰 LUT

- **배울 것**: 시점에 따른 LUT, 지평선을 촘촘히 한 위도 매핑, 방위각을 해 기준으로 재는 이유, 고주파(해 원반)를 LUT 밖에 두는 이유,
  비용이 해상도와 무관해지는 것.
- **이론**: 9.
- **직접 쓰기**: `sky_view_uv_from(view, sun, height)`와 그 역: 해 기준 방위각과 지평선 근처를 촘촘히 한 고도각의 매핑(이론 9). 합쳐
  약 15줄. 검사: 왕복이 맞다, 해 방향이 u = 0, 지평선 근처에 텍셀이 많다.
- **만드는 것**: 하늘 뷰 LUT compute(192 × 108, 매 프레임), 하늘 패스가 LUT를 읽는다. 토글 "Sky-view LUT". 하늘 뷰 LUT를 만드는
  compute와 곧은 하늘 패스는 같은 WGSL 함수를 부른다.
- **볼 것**: 그림은 거의 같고, GPU 시간이 해상도에 덜 의존한다.
- **실험**:
  - a. 토글을 끄고 켜며 Scale 1과 4에서 GPU 시간(1단계 실험 d와 비교).
  - b. 차이 보기: 오차가 해 주변과 지평선에 모이는지.
  - c. 높이 오프셋 40 km에서 차이 보기. 예측: 매개화가 높은 곳에서도 맞을까?
- **검증 문제**:
  1. [설명] 이 LUT는 왜 매 프레임 다시 만드나? 무엇이 변수에 들어가나?
  2. [설명] 해 원반을 LUT에 넣으면 어떻게 될까?
  3. [설명] 방위각을 북쪽이 아니라 해 기준으로 재면 무엇이 좋아지나?
  4. [손 계산] 하늘 뷰 LUT의 108줄에서 지평선 근처 한 줄과 천정 근처 한 줄이 덮는 고도각을 구하고 비교하라.
- **다음의 동기**: 하늘은 끝났다. 하지만 물체는 대기 밖에 있는 것처럼 선명하다.

### 6단계: 대기 원근

- **배울 것**: 유한한 거리까지의 같은 적분, color · T + S, 프러스텀 볼륨(froxel)과 깊이 분포, 거리 배율.
- **이론**: 8.
- **직접 쓰기**: `aerial_slice_from_distance(distance)`와 그 역(제곱 분포), 그리고 합성 `color · T + S`. 약 8줄(이론 8). 검사: 왕복,
  가까운 칸이 촘촘하다, 거리 0이면 색이 그대로다. 유한한 거리까지의 적분은 1단계의 루프를 `t_max`만 바꿔 다시 쓴다.
- **만드는 것**: 먼저 프래그먼트마다 곧은 적분, 그 다음 32 × 32 × 32 볼륨 compute와 메시 셰이더. 토글 "Aerial volume",
  `aerial_scale` 파라미터. 쇼케이스의 `aerial_scale`과 노출을 정한다.
- **볼 것**: 먼 바닥과 행성 모형이 하늘 색으로 흐려진다. 해질녘엔 붉게.
- **실험**:
  - a. `aerial_scale` 1 → 100 → 1000. 예측: 1에서 보일까?
  - b. 토글로 곧은 적분과 볼륨 비교, 차이 보기.
  - c. 해를 등지고 볼 때와 해를 향해 볼 때 먼 곳의 색.
- **검증 문제**:
  1. [설명] 하늘과 대기 원근이 "같은 적분"이라는 것은 무슨 뜻인가?
  2. [설명] 볼륨이 투과율을 RGB가 아니라 회색 하나로 담는 근사는 무엇을 잃나?
  3. [설명] 거리 칸을 제곱 분포로 나누는 이유는?
  4. [유도] 물체에서 눈까지의 시선에 이론 5의 적분을 쓰면 왜 color · T + S의 꼴이 되나?
  5. [손 계산] 지면 근처 Rayleigh 파랑 채널만으로, 거리 100 m와 `aerial_scale` 50에서 T를 구하라(1% 안).
- **다음의 동기**: 그늘 속이 여전히 씬의 고정된 주변광(`lighting`의 `ambient`)이다. 해의 높이와 상관없이 같은 색이다.

### 7단계: 하늘의 주변광

- **배울 것**: radiance에서 irradiance로(코사인 가중 반구 적분), 지면에서 튀는 빛.
- **이론**: 10.
- **직접 쓰기**: `sky_irradiance(radiance_at, normal)`: 반구를 격자로 나눠 입체각과 코사인으로 가중해 더한다(이론 10). 약 15줄.
  검사: 모든 방향의 radiance가 1이면 위를 보는 면의 조도가 π(1% 안), 옆을 보는 면은 그 절반의 하늘과 절반의 지면.
- **만드는 것**: 하늘 뷰 LUT를 반구 적분하는 compute(위 조도, 아래 조도), 메시 셰이더가 법선의 y로 섞는다. 토글 "Sky ambient"(끄면
  씬의 `lighting`/`ambient`). 그래프 대신 Study 섹션에 두 조도의 색 견본.
- **볼 것**: 한낮에 그늘이 푸르스름하고, 해질녘엔 전체가 붉고 어두워진다.
- **실험**:
  - a. 토글을 끄고 켜며 그늘 속 색. 예측: 한낮의 그늘은 무슨 색일까?
  - b. `ground_albedo` 0 → 1. 예측: 무엇의 어느 쪽이 밝아질까?
- **검증 문제**:
  1. [설명] 위를 보는 면과 옆을 보는 면의 하늘 조도가 다른 이유는?
  2. [설명] 하늘의 radiance에 π를 곱한 것(0번)이 여기서 왜 맞아떨어지나?
  3. [유도] 모든 방향의 radiance가 L로 같을 때, 위를 보는 면의 조도가 πL임을 반구 적분으로 보여라.

### 8단계: 최적화

- **배울 것**: 비용 모델, 계산 대 대역폭, 믿을 만한 측정, 걸음 수와 샘플 분포, LUT 해상도와 형식, 다시 만들지 않기, 그리기 순서, workgroup
  크기, 기기별 품질 설정. 최적화마다 무엇을 내주나(정확도, 지연, 메모리).
- **이론**: 11(과 9).
- **측정 환경**: 사용자의 랩탑, D3D12 빌드(다른 세션에서 진행 중인 포팅이 끝난 뒤). 그 전에는 구현과 정확성(차이 보기)만 확인하고, 숫자는
  재지 않거나 참고로만 적는다. 목표 시간은 미리 정하지 않는다: 숫자를 먼저 보고 판단한다(결정 11, 12).
- **직접 쓰기**: `ray_march_sample(index, count, t_max, distribution)`: 걸음 하나의 위치와 길이(가중치). 균일, 제곱, 지수 분포. 약 10줄.
  검사: 가중치의 합이 t_max, 균일 밀도에서 어느 분포든 정확, 지수 밀도(대기)에서 같은 걸음 수로 오차가 균일보다 작다.
  그리고 `steps_for_length(t, min_steps, max_steps)`: 시선 길이에 따른 걸음 수, 몇 줄.
- **만드는 것**: 아래 최적화마다 Study 섹션의 토글이나 슬라이더(0이 지금의 기본), 패스마다의 GPU 시간(아래 "측정"), 차이 보기로 정확도의 대가를
  본다. 채택한 것은 기본값을 바꾸고 "구현 결과"에 전후의 숫자를 적는다.

  | 최적화 | 무엇을 바꾸나 | 대가 |
  |---|---|---|
  | 시선 길이에 따른 걸음 수 | 하늘 뷰 LUT, 대기 원근 볼륨, 곧은 적분의 걸음 수를 min..max에서 시선 길이로 정한다(Hillaire) | 짧은 시선의 정확도 |
  | 비균일 샘플 분포 | 걸음을 카메라와 지면 가까이 촘촘히(직접 쓰기의 분포) | 없음에 가깝다: 같은 걸음 수로 오차가 준다 |
  | LUT 해상도 | 하늘 뷰 96 × 54 ~ 384 × 216, 대기 원근 16³ ~ 64³, 투과율 128 × 32 ~ 512 × 128 | 지평선, 해 주변, 먼 곳의 오차 |
  | LUT 형식 | 16비트 대 32비트 부동소수점(백엔드가 스토리지로 허용하는 것). WebGPU에서 32비트 부동소수점 텍스처의 선형 필터는 `float32-filterable` 기능이 있어야 한다: 없으면 이 실험은 D3D12 빌드에서만 한다 | 정밀도 대 대역폭 |
  | 다시 만들지 않기 | 하늘 뷰 LUT는 카메라 높이, 해 방향, 대기 값이, 대기 원근 볼륨은 그에 더해 카메라의 방향과 시야가 그대로면 지난 것을 쓴다. Edit 모드에서 카메라가 멈춰 있으면 둘 다 0 ms | 입력을 하나라도 빠뜨리면 틀린 그림이 남는다(시험으로 막는다) |
  | 나눠서 다시 만들기 | 대기 원근 볼륨을 프레임마다 일부 칸만 다시 만든다 | 카메라가 빨리 돌 때 한두 프레임 늦은 안개 |
  | 그리기 순서 | 하늘을 메시 앞(깊이 검사 없이)에 그릴 때와 뒤(지금)에 그릴 때 | 실험용: 가린 픽셀을 계산하는 값 |
  | 대기 원근을 정점에서 | 메시의 정점마다 (T, S)를 구해 보간한다(볼륨을 읽지 않음) | 큰 삼각형에서 부정확 |
  | workgroup 크기 | compute의 4 × 4, 8 × 8, 16 × 16; 다중 산란의 공유 메모리 리덕션 대 루프 | 기기마다 최적이 다르다 |
  | 기기별 품질 | 폰 UI(터치)에서 작은 LUT와 적은 걸음(그림자가 터치 화면에서 1024인 것과 같다) | 폰의 그림 |
- **볼 것**: 패스마다의 GPU 시간과 차이 보기가 함께 바뀐다. 어떤 최적화는 크게, 어떤 것은 거의 효과가 없다.
- **실험**: 최적화마다 예측(몇 ms가 줄까? 어디에 오차가 생길까?) → 측정 → 차이 보기. 특히:
  - a. Scale 1과 4, Fixed 320 × 180에서 곧은 하늘과 하늘 뷰 LUT의 시간. 예측: LUT가 지는 해상도가 있을까?
  - b. 비균일 분포를 켜고 같은 오차가 되는 최소 걸음 수를 찾는다.
  - c. LUT 형식을 바꿔 시간이 바뀌는지 본다. 예측: 이 패스는 계산과 대역폭 중 어느 쪽이 막혔나?
  - d. "다시 만들지 않기"를 켜고 Edit 모드에서 카메라를 멈췄을 때와 돌릴 때.
  - e. 같은 설정을 다섯 번 재서 흔들림의 크기를 본다. 예측: 0.05 ms의 차이를 믿을 수 있나?
- **검증 문제**:
  1. [손 계산] 1920 × 1080에서 곧은 하늘(N = 32, M = 16)과 하늘 뷰 LUT(192 × 108, N = 32, 투과율 LUT 있음)가 매질을 몇 번 계산하나? 몇 배 차이인가?
  2. [설명] LUT 형식을 반으로 줄였는데 시간이 그대로라면 무엇을 알 수 있나?
  3. [설명] 대기 원근 볼륨을 "다시 만들지 않기"에 넣을 때 입력으로 무엇을 비교해야 하나? 하나를 빠뜨리면 화면에 무엇이 보이나?
  4. [참/거짓] "LUT를 쓰면 항상 빨라진다." 이유와 함께.
  5. [설명] GPU 시간을 한 프레임만 보고 비교하면 안 되는 이유는?
  6. [설명] 하늘을 불투명 메시 뒤에 그리는 것이 왜 최적화인가? reverse Z와 `GreaterEqual`이 여기서 하는 일은?

### 종합 검증 (8단계 뒤)

새 코드 없이, 전체를 이었는지 본다. 채점은 3절과 같다.

1. **[설명] 한 픽셀의 여정.** 해에서 나온 빛이 화면의 하늘 픽셀 하나가 되기까지를 물리로(투과율, 산란, 위상 함수, 다중 산란), 그리고 이
   엔진이 그 값을 어떤 LUT와 패스로 계산하는지(무엇이 언제 다시 만들어지는지) 처음부터 끝까지 설명하라. 같은 일을 메시의 한 픽셀(햇빛의
   색, 주변광, 대기 원근)에 대해서도.
2. **[전이] 화성.** 화성의 하늘은 낮에 주황빛이고 해질녘 해 주변은 파랗다. 대기가 얇고 미세한 먼지가 많다는 것만으로, 이 스펙의 모델의
   말(계수의 파장 의존, 위상 함수, 투과율)로 설명하라. 이 엔진에서 재현하려면 `NvAtmosphere`의 무엇을 바꿔야 하나?
3. **[설계] 값이 바뀌면.** 대기의 꼭대기가 두 배 높아지면, 해가 지평선 아래로 가면, 카메라가 10 km 올라가면: 각각 어느 LUT를 다시 만들고
   그림의 무엇이 어떻게 바뀌나?
4. **[설계] 비용.** 1080p에서 4K로 바꾸면 각 패스의 시간이 어떻게 바뀔지 예측하고 이유를 대라(어느 것은 픽셀에, 어느 것은 LUT 크기에 따른다).
5. **[참/거짓] 오개념 다섯.** Claude가 단계들에서 다룬 개념으로 낸다(이유와 함께 답한다).

결과는 "구현 결과"의 맨 끝에 적는다.

### LUT와 패스

LUT는 `RGBA16Float`: compute에서 쓰기 전용 스토리지 텍스처로 쓰고, 셰이더에서 선형 필터로 읽는다(둘 다 WebGPU 코어).

| LUT | 크기 | 변수 | 언제 만드나 | 단계 |
|---|---|---|---|---|
| 투과율 | 256 × 64 | (h, μ), 지평선 근처를 촘촘히 | 대기 값이 바뀐 프레임 | 3 |
| 다중 산란 | 32 × 32 | (h, μ_sun) | 대기 값이 바뀐 프레임, 투과율 다음 | 4 |
| 하늘 뷰 | 192 × 108 | (해 기준 방위각, 지평선 근처를 촘촘히 한 고도각), 카메라 높이와 해 방향 | 매 프레임 | 5 |
| 대기 원근 | 32 × 32 × 32 | 화면 uv × 거리 칸(제곱 분포). rgb 산란, a 투과율(회색) | 매 프레임 | 6 |
| 하늘 조도 | 버퍼, 색 둘 | 위 반구, 아래 반구 | 매 프레임 | 7 |

- "대기 값이 바뀌었다"는 `NvAtmosphere`의 매질 필드를 지난번과 비교해 안다(그림자 맵이 크기와 형식을 비교하는 것과 같다).
- compute 패스는 파티클 패스와 함께 그림자 패스 전에 기록한다. 대기가 꺼진 동안은 1 × 1 텍스처가 묶인다(`bloom_dummy`와 같다).
- 토글로 꺼진 LUT는 만들지 않는다(비용 비교가 정직하도록).

### 씬 패스

그리기 순서: 불투명 메시, **하늘**, 데칼, 디버그 라인, 선분, 알파 파티클, 가산 파티클.

| 주제 | 결정 |
|---|---|
| 하늘 | 화면 삼각형, 깊이 0(reverse Z의 가장 먼 곳), 비교 `GreaterEqual`, 깊이 쓰기 없음: 메시가 그리지 않은 픽셀만 남는다. 시선은 역 view-projection으로. 대기가 꺼지면 그리지 않고 `clear_color`가 보인다 |
| 파이프라인 | `NV_SCENE_FORMAT`, `renderer->scene_samples`. MSAA가 바뀌면 함께 다시 만든다 |
| 햇빛의 색 | `frame.light_color` = E_sun × 카메라 높이에서 해 방향의 투과율(C가 계산). 씬이 100 m 안이라 높이 차이는 버린다 |
| 대기 원근: 메시 | `fs_main`의 끝에서 color · T + S. 볼륨을 화면 uv(프래그먼트 위치 / 씬 해상도: 씬은 큰 타깃의 왼쪽 위에 그려진다)와 거리로 읽는다 |
| 대기 원근: 이펙트 (9단계) | 알파: color · T + S · alpha, 가산: color · T. 디버그 라인은 그대로 |
| 거리 배율 | `aerial_scale`이 대기 원근에서만 거리에 곱해진다(Unreal의 "Aerial Perspective View Distance Scale"). 볼륨이 덮는 거리는 카메라 `far` × 배율 |
| 그림자, 업스케일 패스 | 바뀌지 않는다 |

### 엔진

새 모듈 `engine/atmosphere.h`, `engine/atmosphere.c`: 설정, 지구 기본값, CPU의 적분(정답, ctest와 프로브와 그래프가 쓴다). GPU 쪽은
bloom처럼 `renderer.c`에 둔다. WGSL의 적분 함수는 C 함수와 같은 이름, 같은 순서로 쓴다.

```c
// engine/atmosphere.h
// Physical sky and aerial perspective (docs/specs/atmosphere.md). Zeroed: no atmosphere.
typedef struct NvAtmosphere {
    b32 on;
    f32 rayleigh_scattering[3]; // per km, at the ground
    f32 rayleigh_height;        // km, where the density falls to 1/e
    f32 mie_scattering;         // per km, at the ground
    f32 mie_absorption;         // per km, at the ground
    f32 mie_height;             // km
    f32 mie_anisotropy;         // Cornette-Shanks g, 0..0.99
    f32 ozone_absorption[3];    // per km, at the layer's peak
    f32 ground_albedo[3];
    f32 sun_disk;               // the sun's angular diameter, degrees; 0 = no disk
    f32 aerial_scale;           // distances count this many times in aerial perspective; 0 = no aerial perspective
} NvAtmosphere;

typedef enum NvAtmosphereView {
    NV_ATMOSPHERE_VIEW_FINAL,
    NV_ATMOSPHERE_VIEW_TRANSMITTANCE, // T along each view ray
    NV_ATMOSPHERE_VIEW_SINGLE,        // single scattering only
    NV_ATMOSPHERE_VIEW_MULTIPLE,      // multiple scattering only
    NV_ATMOSPHERE_VIEW_RAYLEIGH,
    NV_ATMOSPHERE_VIEW_MIE,
    NV_ATMOSPHERE_VIEW_DIFFERENCE,    // |LUT path - direct path| / direct path, times difference_gain
    NV_ATMOSPHERE_VIEW_COUNT,
} NvAtmosphereView;

// Study tools (docs/specs/atmosphere.md, "공부 도구"). Zeroed: every optimization on, the final image.
typedef struct NvAtmosphereStudy {
    NvAtmosphereView view;
    b32 no_transmittance_lut;   // integrate toward the sun at every step instead
    b32 uniform_transmittance;  // map the transmittance LUT evenly, without crowding the horizon
    b32 no_multiple_scattering;
    b32 no_sky_view_lut;        // integrate every sky pixel
    b32 no_aerial_volume;       // integrate every fragment's ray
    b32 no_sky_ambient;         // NvRenderer.ambient (the scene's) instead
    u32 view_steps, sun_steps;  // of the direct integrals; 0 = 32, 16
    f32 altitude;               // km added to the camera's, for the atmosphere only
    f32 difference_gain;        // 0 = 10
    b32 skip_sky;               // draw no sky (the clear color): the sky's share of the scene pass, by difference
    // Step 8's optimizations; 0 is the default, which step 8 changes for the ones it adopts.
    b32 fixed_steps;            // the same step count for every ray, not by its length
    u32 sample_distribution;    // 0 uniform, 1 squared, 2 exponential
    u32 sky_view_scale;         // LUT sizes in quarters of the default: 0 = 4 (the default), 2 = half, 8 = double
    u32 aerial_scale_size;      // the same for the aerial volume
    b32 full_precision;         // 32-bit float LUTs instead of 16-bit
    b32 always_rebuild;         // rebuild the view-dependent LUTs every frame even when their inputs did not change
    u32 aerial_slices_per_frame;// 0 = all
    b32 sky_first;              // draw the sky before the meshes, without the depth test
    b32 aerial_per_vertex;
    u32 workgroup_size;         // 0 = 8 x 8
} NvAtmosphereStudy;

// One view ray's light, split as the study tools show it (radiance times pi: the engine's units).
typedef struct NvSkySample {
    NvVec3 rayleigh, mie, multiple, ground, sun_disk;
    NvVec3 transmittance;
} NvSkySample;

NvAtmosphere nv_atmosphere_earth(void); // Earth's values (Hillaire 2020), with `on` set

// The light that reaches a point `altitude` km above the ground from a direction `cos_zenith` from straight up, 0..1 per
// channel; 0 where the ray hits the planet.
NvVec3 nv_atmosphere_transmittance(const NvAtmosphere* atmosphere, f32 altitude, f32 cos_zenith);

// The sky along `view` (unit, world) seen from `altitude` km with the sun toward `sun` (unit) giving `sun_illuminance`: the
// direct integral the GPU's reference path does too.
NvSkySample nv_atmosphere_sky(const NvAtmosphere* atmosphere, f32 altitude, NvVec3 view, NvVec3 sun, NvVec3 sun_illuminance,
                              u32 view_steps, u32 sun_steps);

// Debug study tool (step 4): adds `paths` Monte Carlo paths along `view`, every order of scattering and no approximation, to
// `sum` and `sum_squares` (for the mean and its standard error). Called a few hundred paths a frame, so the page keeps running.
void nv_atmosphere_path_trace(const NvAtmosphere* atmosphere, f32 altitude, NvVec3 view, NvVec3 sun, NvVec3 sun_illuminance,
                              u32 paths, u64* random_state, NvVec3* sum, NvVec3* sum_squares);
```

`NvRenderer`에 `NvAtmosphere atmosphere`, `NvAtmosphereStudy atmosphere_study`(앱이 매 프레임 설정, `shadows`, `post`와 같다), LUT,
파이프라인, 프로브 요청과 결과, 만든 횟수, 패스마다의 GPU 시간이 생긴다. `FrameUniforms`에 `inverse_view_proj`와 대기 값이 더해진다.

### 측정

**지금 있는 것** (WebGPU 판, `engine/renderer.c`): 쿼리 세트 하나(`NV_TIMESTAMP_COUNT` 12칸)에 패스마다 시작과 끝의 칸 번호를 손으로
정해 `timestampWrites`로 쓰고, 프레임 끝에 한꺼번에 읽어 와 패스마다의 필드(`gpu_ms`, `gpu_shadow_ms`, `gpu_upscale_ms`, `gpu_bloom_ms`,
`gpu_particles_ms`)에 ms로 넣는다. 값은 몇 프레임 늦게 오고, 읽기가 진행 중인 프레임은 재지 않는다. 기기에 타임스탬프가 없으면 0이다.
샌드박스는 그것을 `FrameTimes`로 옮겨 Stress 탭에 1초 평균으로 보인다. 일반적인 "이름 붙은 GPU 타이머" API는 없다: 패스 하나를 더 재려면
칸 번호, `NV_TIMESTAMP_COUNT`, 읽는 줄, 필드, `FrameTimes`, Stress 탭을 각각 고친다. 패스 안의 일부는 잴 수 없다(WebGPU 코어는 패스 안의
타임스탬프를 허용하지 않는다).

**이 스펙이 더하는 것**:
- 대기의 LUT는 패스마다 따로 compute 패스로 기록하므로 패스마다 잴 수 있다: 투과율, 다중 산란, 하늘 뷰, 대기 원근, 하늘 조도. 하늘은 씬 패스
  안이므로 `skip_sky`를 끄고 켠 차이로 잰다(패스를 나누면 MSAA 색과 깊이를 한 번 더 읽고 써야 해서 잰 값이 실제와 달라진다).
- 다섯 패스를 더하면 같은 방식으로 다섯 군데를 손으로 고쳐야 한다. 그래서 타이머를 표 하나로 모으는 작은 정리(이름과 칸을 한 표에서 정하고,
  읽기와 평균을 한 곳에서)를 제안한다. 다만 D3D12 포팅이 다른 세션에서 렌더러를 바꾸고 있으므로, 정리는 **포팅이 끝난 뒤 그 구조에 맞춰** 한다
  (충돌을 피하고, D3D12의 타임스탬프 쿼리 힙도 같은 표를 쓰게). 그 전의 단계(3~7)는 기존 방식대로 칸을 더하거나 차이로 잰다.
- 숫자는 사용자의 랩탑에서 D3D12 빌드로 잰다(결정 12). 브라우저와 CI의 swiftshader 숫자는 성능 판단에 쓰지 않는다.

**연습 시험** (`tests/atmosphere_exercise.c`, ctest 밖, `cc`로 돈다): 단계마다 그 단계의 "직접 쓰기" 검사. 리뷰가 끝나면 그 검사가
`tests/atmosphere_test.c`로 옮겨 가고, 연습 파일은 다음 단계의 검사로 바뀐다.

**ctest** (`tests/atmosphere_test.c`, `engine/atmosphere.c`만; 씬 파일은 `tests/scene_file_test.c`):

- 씬 파일: `lighting` 안의 `atmosphere`를 읽는다. 키를 빼면 기본값, 범위 밖의 값, 모르는 키, `atmosphere`를 두 번 쓰면 줄 번호와 함께 오류.
  `atmosphere`가 없으면 대기가 없다. (0단계)

- 천정 투과율이 손 계산(약 0.940, 0.868, 0.762)과 1% 안. 고도가 낮을수록 줄고 파랑이 먼저 준다. 행성을 맞히면 0, 대기 밖은 1. (0단계)
- 하늘: 천정이 파랗고(b > r), 해가 2°일 때 해 쪽 지평선이 붉고(r > b), 걸음 수를 늘리면 값이 수렴한다(64와 128의 차이 < 0.5%). (1단계)
- 위상 함수를 구 위에서 적분하면 1(수치 적분, 1%). Mie가 있으면 해 쪽이 반대쪽보다 밝다. (2단계)
- 샘플 분포: 가중치의 합이 t_max, 지수 밀도에서 비균일 분포의 오차가 균일보다 작다. (8단계)

**Playwright** (Release와 Debug, swiftshader). 단계마다 그 단계의 줄이 더해진다.

| 시험 | 단계 |
|---|---|
| 해를 낮추면 바닥 픽셀이 붉어진다. 파라미터를 바꾸면 undo 한 걸음(Scene settings), 저장 왕복이 같다, 다시 불러오면 값이 남는다. Play와 Stop 뒤 `save_crc`가 같다. 대기가 없는 씬(스트레스, 체스)은 그림이 전과 같다 | 0 |
| 하늘 픽셀이 파랗다. **프로브: GPU의 곧은 적분과 C가 하늘 픽셀 셋(천정 근처, 해 반대편, 지평선)에서 1% 안** | 1, 2 |
| MSAA 끔/4x, Scale 2, Fixed에서 같은 결과, WebGPU 오류 없음, 성분 보기마다 오류 없음 | 1 |
| **LUT 경로와 곧은 경로가 해의 고도 45°, 10°, 2°에서 하늘 픽셀 셋에서 상대 5% 안**(해 원반 근처 제외). 해를 돌려도 투과율 LUT 횟수가 그대로, `rayleigh`를 바꾸면 1 오름 | 3, 4, 5 |
| `aerial_scale` 1000에서 먼 바닥이 1보다 하늘 색에 가깝다. 볼륨과 프래그먼트별 곧은 적분이 5% 안 | 6 |
| 최적화마다 차이 보기가 정한 허용 안. "다시 만들지 않기": 카메라와 해가 그대로면 만든 횟수가 오르지 않고, 카메라 높이, 해, 대기 값, (볼륨은) 카메라의 방향이나 시야 중 하나만 바꿔도 오른다 | 8 |

정답의 사슬: ctest(손 계산 ↔ C) → 프로브 시험(C ↔ GPU 곧은 적분) → 차이 시험(GPU 곧은 적분 ↔ GPU LUT).

## 용어

| 한국어 | 영어 | 뜻 |
|---|---|---|
| 복사휘도 | radiance (L) | 한 방향에서 오는 빛의 세기 |
| 복사조도 | irradiance (E) | 면에 떨어지는 빛의 총량 |
| 참여 매질 | participating media | 빛을 흡수하고 산란하는 기체, 연무 |
| 산란 / 흡수 / 소멸 계수 | scattering / absorption / extinction coefficient (σ_s, σ_a, σ_t) | 단위 거리당 빛이 꺾이는 / 사라지는 / 둘을 합친 비율 |
| 광학 깊이 | optical depth (τ) | 경로를 따라 적분한 소멸 계수 |
| 투과율 | transmittance (T) | exp(−τ), 경로를 지나 남는 비율 |
| 위상 함수 | phase function (p) | 꺾이는 각도의 분포 |
| 비등방성 | anisotropy (g) | 앞쪽으로 꺾이는 정도 |
| 스케일 높이 | scale height (H) | 밀도가 1/e가 되는 높이 |
| 단일 / 다중 산란 | single / multiple scattering | 한 번 / 여러 번 꺾인 빛 |
| 대기 원근 | aerial perspective | 먼 물체가 대기에 흐려지는 것 |
| 레이 마칭 | ray marching | 시선을 걸음으로 나눠 적분하는 것 |
| 매개화 | parametrization | 변수를 텍스처 좌표로 펼치는 방법 |
| 프록셀 | froxel | 화면 칸 × 깊이 칸의 볼륨 셀 |
